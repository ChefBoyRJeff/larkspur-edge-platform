# Larkspur Edge v1.0.0 (11-27-2026)

The first complete release: Larkspur Track running on site in dev and prod, delivered by GitOps, monitored, backed up to Azure, syncing to Azure, and tested by failure drills. The plan's modules are all done (`docs/plan.md`).

## Measured

|---|---|
| Releases and rollbacks | No failed requests during rolling releases (0 of 379 and 0 of 514 probes); rollback by revert about 30 s |
| Alerts | A database outage alerted after 332 s and resolved by email |
| Backups | WAL in Azure 2–5 s after it closes; restore drills 71 and 81 s, all rows and a marker present |
| Database lost with its volume (dev) | Rebuilt from Azure by Argo CD, ready in 60 s, nothing lost; the app needed a restart |
| Internet link cut (dev) | 7 of 7 events made during a 48 s outage, with a worker restart, reached Azure 5 s after the link returned; no duplicates |
| Bad release (dev) | Users unaffected (593 of 593 requests); after the fixes, a revert is picked up on the next retry and the release alerts within 5 minutes |
| Worker node powered off | After the fixes: 0 of 498 prod and 1 of 499 dev requests failed; alert email kept working; node back 21 s after power-on |

## Known limits
- `lark-k3s-01` is a single point of failure: it runs the only control plane and holds every volume (both databases, Prometheus).
- k3s runs one CoreDNS; it moves to the other node about 5 minutes after a node loss.
- The Sealed Secrets key is not backed up; a new cluster needs every secret sealed again (`docs/install.md`).
- After a database is rebuilt, the web and sync pods must be restarted (new database password).
- Nothing reads the Azure queues yet; messages wait there (they never expire).
- The install guide has not been run end to end on spare hardware.
- Credentials expire in November 2027 (backup 11-25-2027, sync 11-26-2027) and must be rotated before then.
